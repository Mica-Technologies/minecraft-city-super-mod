# Mast Arm Curve System

The upsweep section of a signal mast arm: the piece that leaves the pole at an angle, curves
over, and hands off level to the horizontal arm that crosses the road. This document covers the
realistically scaled OBJ family (`trafficpolemastarmcurve*`). It does **not** cover the
horizontal arm itself, which is unchanged (`trafficpolehorizontal` and friends).

## Why the old one is small, and why a new one was needed

`trafficpoleverticalcurveconnector` is the original upsweep. Two facts about it explain
everything:

* Its model spans `z: -16 → 32` and `y: -12 → 12`. Those are the **hard legal limits** of a Forge
  JSON element model. It is not small by choice — it is already as large as the format permits.
* It is not a curve. It is 130 stacked slabs, each 0.75 deep, each stepping 0.25 in y: a
  constant-slope ramp with a staircased silhouette.

Real curved mast arms cover 10–25 ft of run and 4–10 ft of rise, leave the pole at roughly
20–35°, and arrive at the horizontal run with **zero** slope so the joint does not kink. None of
that fits in one JSON model. It fits easily in OBJ, which the mod loads
(`OBJLoader.INSTANCE.addDomain("csm")` in `CsmClientProxy`) and which has no coordinate limit.

The old blocks remain registered and untouched.

## One curve is several blocks

Each curve is a connected staircase of **real blocks**, one per cell its centerline passes
through, and each cell draws its own slice of one continuous sweep.

A single block carrying the whole sweep as one large OBJ would have been far less work. It was
rejected for three reasons, in order of how badly they bite:

1. **Culling.** A block model is baked into the chunk section VBO of the block that owns it. A
   6-block arm hanging off one block disappears the moment that block's section is frustum-culled
   while the arm's span is still on screen. The old JSON connector already has a mild version of
   this, since it draws three blocks of geometry from one.
2. **Nothing mounts to air.** Signal heads, signs and luminaires attach to blocks. With one block,
   nothing could ever hang off the curved part — and real intersections hang things there.
3. **Auto-connect works on block adjacency.** The pole mounting system reads neighbouring block
   positions. Empty air is invisible to it, permanently.

Geometry stays continuous across cells because a band is drawn *whole* from whichever cell owns
it. An OBJ is allowed to leave its own block; it just must not be the only thing keeping it on
screen, which is precisely the distinction the multi-block layout preserves.

## The curve

The centerline is a parabola. That is not an aesthetic pick — it is the unique quadratic meeting
the two hard constraints. Writing `t` for blocks travelled from the pole:

```
y(t) = rise * (2t/run - t²/run²)
```

`y(0) = 0`, `y(run) = rise`, and `y'(run) = 0` — level at the handoff. The entry slope
`2·rise/run` therefore falls out of the chosen size rather than being tuned per preset, so the
entry angle is a **derived, reportable** number and every preset is automatically consistent
with every other.

The tube tapers from 9.2 units across at the root to 8 at the tip, and swells back to 10 over the
last third of a block as the boot. The 8 is not free: it is the diameter of
`trafficpolehorizontal`, the block this has to mate with. The far ring lands on the block boundary
plane so that join is flush.

curve matches the pole under it.

```
models/block/trafficaccessories/shared_models/mastarmcurve_<preset>_c0_ped.obj

                                                       poles"), plus _<dir> stubs only where
                                                       they differ from the large root's
models/block/trafficaccessories/shared_models/mastarmcurve_<preset>_inv.obj    inventory icon
models/block/trafficaccessories/shared_models/mastarmcurve.mtl                 shared, one material
blockstates/trafficpolemastarmcurve<preset><colour>.json                       25 files
src/main/java/.../trafficaccessories/MastArmCurveProfile.java                  GENERATED enum
```

Hand-written:

```
src/main/java/.../trafficaccessories/BlockTrafficPoleMastArmCurve.java
src/main/java/.../trafficaccessories/TileEntityMastArmCurve.java
```

**`MastArmCurveProfile.java` is generated, deliberately.** It holds the cell list and the
per-cell hitbox, and the placement code has to agree exactly with the list the geometry was split
on. If those two ever drifted, a curve would place a block with no model in it, or draw a slice
of tube in mid-air with no block behind it. Emitting both from one source removes the failure
mode rather than documenting it. Re-run the generator after any preset change; it clears the
models and blockstates it owns first, so a stale cell file from an old cell count cannot survive
(one did, once).

## Implementation notes

**Cell index lives in a tile entity.** Block metadata is four bits, and the horizontal facing
already needs two of them, leaving four states where up to twelve are required. Same constraint
and same solution as `TileEntityFireAlarmSoundIndex`. `getActualState` reads the index; the
blockstate's `shape` property exists only in actual state, never in meta.

**Placement is the pole family's inherited rule: the arm reaches away from the face you
clicked.** Click the side of a pole and the arm sweeps out from it. That is what every other CSM
pole accessory does, and it is the orientation the pole-end boot is built for.

An earlier version overrode `getStateForPlacement` to send the arm the way the player was
*looking*. It reads well when placing on top of a pole and it makes the realistic side mount
impossible to aim: to click a pole's north face you must stand north of it looking south, which
would have pointed the arm back into the pole. Reverted.

**The arm is cut against the pole itself.** See "The pole joint" below — it is the part of this
model that took the most attempts to get right.

**All or nothing.** `onBlockPlacedBy` validates every cell before placing any of them. A partly
built curve would draw a tube stopping in mid-air and would leave orphan cells when broken. If
anything is in the way the root is removed, the item is returned (survival), and the blocking
position is reported in the status bar.

**Breaking any cell takes the whole curve, and drops one item.** A cell knows its index, and
index plus facing locates the root, so no cell stores a position that could go stale. Siblings
are removed with `setBlockToAir`, which does not drop — so a curve costs exactly one item however
it is dismantled. A thread-local guard stops a sibling's removal from starting a fresh demolition.

**Hitboxes are measured, not guessed.** The generator reads each cell's mesh bounds, clamps them
to the block, and writes them into the enum. Geometry overhanging into the next cell is covered
by that cell's own box, because every cell is a placed block. The box is returned for the
unrotated (north) orientation only — `AbstractBlockRotatableNSEW.getBoundingBox` applies the
facing rotation itself, and rotating in `getBlockBoundingBox` as well turns it twice.

**Poles do not sprout a stub into a curve.** `BlockTrafficPoleMastArmCurve` implements
`ICsmTrafficPoleIgnored`. The curve carries its own boot where it meets
the pole, which is exactly the hardware a mount stub depicts; both would be two contradictory
connections on one joint.

## Mount hardware

Every cell grows a band-bracket-plate assembly toward any of its four sides — model up, down,
east and west — with something mountable against it, the same way a pole does. Along the arm
there is no stub: that is where the arm itself goes. The mountability test is
`AbstractBlockTrafficPole.isMountableAdjacent`, shared rather than reimplemented, so a curve
ignores exactly what a pole ignores. (That method was widened from `protected` to `public` for
this; the curve is deliberately *not* an `AbstractBlockTrafficPole` subclass, because that class
is six-way rotatable and a curve is horizontal-only.) The list already contains
`BlockTrafficPoleMastArmCurve`, which is what stops one cell of a curve from sprouting hardware
into the next cell of the same curve.

**Hardware is per cell and per direction — 4 files per cell, 164 in all.** On a pole one model
serves everywhere because a pole is a straight tube centred in its block. A curve cell's tube is
neither centred nor level, and its pose differs in every cell, so a shared model would float off
the tube in most of them.

**The band goes at the point of the tube closest to the face centre, not at the cell's middle.**
Those are not the same point. Several cells in every preset only clip a corner of their block —
6x2's cell 1 holds only the last 3 units of its column — so the middle of the cell has no tube in
it at all, and hardware placed there would hang in the air.

**Only the bracket is allowed to slant.** The bracket leaves the tube at whatever angle the tube
sits at, but the end plate's axis is the *face's* normal, so it lies flat against the block it
bolts to. Building the plate square to the bracket instead leaves it visibly tilted against a
flat surface.

### Why one `shape` property instead of five

The blockstate keys both the cell model and its stub submodels off a single `shape` property
holding `cell * 16 + mountMask`. That is forced, not preferred.

A stub model depends on **both** the cell and the direction. Forge blockstate variants compose
independent property blocks, and a property block can only choose a model from its own value — so
a mount property would have to carry the cell index rather than a boolean. Four 13-value mount
properties beside `cell` and `facing` is **1,370,928** block states, and `BlockStateContainer`
materialises every one of them eagerly. Packing the same information into one property is **768**
— exactly what four plain booleans would have cost, while still letting each stub match the tube
it clamps to.

The cost is blockstate size: 16 mask values per cell means up to 192 variants per file, about
2.5 MB of generated JSON across the 25 files. `MastArmCurveProfile.shapeIndex` is the one
definition of the packing, and the generator writes both sides of it.

Which pole is behind the root is one more thing only the root's model depends on, and it goes
into the same property for the same reason: the two narrow-pole roots take the slots after the
last cell (`cellCount + 0` for the thin pole, `+ 1` for the pedestal), so a 12-cell preset is
`(12 + 2) × 16 × 4 = 896` states rather than 768. `MastArmCurveProfile.shapeIndex(cell, mask,
fit)` is the instance-side of that packing.

## The pole joint

The arm's pole end is **saddle-cut against the pole's own cylinder**, and it swells into a boot
as it approaches. Three earlier versions of this joint were wrong, each for its own reason, and
the reasons are worth keeping:

1. **Sheared onto a plane.** The end ring slid bodily along the tangent onto the pole face. An
   oblique cut through a tube is an ellipse stretched by `1/cos(theta)`, so the slid ring came out
   far taller than the ring behind it and the surface folded back on itself — near-degenerate,
   inside-out triangles along the top of the arm, exactly where it meets the pole.
2. **Clipped rail by rail against a flat plane.** Correct geometry, wrong surface. A pole is
   round, so a flat cut is at the right depth only along the arm's centreline; at the arm's flanks
   the pole's skin has receded 2.7 units further back and the cut face hangs in open air.
3. **Covered with a flat elliptical collar.** To hide (2), a collar 12.4 units across was placed
   over the joint — against a pole 12 units across. That cannot work at any angle, and it showed
   as flat slivers either side of the pole. The lesson is one subtraction: anything meant to hide
   behind the pole must be **narrower than 12**.

The current joint solves all three at once. Every angular rail of the tube is clipped where it
crosses the pole's cylinder, so the arm lands on the pole's skin everywhere at once — to machine
precision, which the generator can assert. There is no separate collar at all: the boot is part
of the tube's own radius profile, so there is only ever one surface here and nothing to bleed
through. `R_BOOT` is 5.0 because it has to disappear behind two things — the pole (12 across) and
`trafficpoleverticalconnectorangled*`, the existing block for this joint, whose boss is 10 across
and 11 tall.

**Finding the crossing needs the first root, not any root.** Depth into the pole is negative on
*both* sides of it — keep walking backwards and a rail comes out the far side — so a plain
bisection over a wide bracket is as likely to land on the exit as the entry, and the exit is
forty-odd units away through the middle of the pole. The generator scans backwards in small steps
from a parameter known to be outside, then bisects the first bracket that straddles the skin.

### Narrow poles: the bracket

The saddle cut assumes the pole is wider than the arm. It is, for the 12-across pole family the
curve was built against — and it is not for the two thinner poles CSM has since grown: the thin
traffic pole (`trafficpolehorizontal*`, 8 across) and the pedestal pole (`trafficpolepedestal*`,
6 across). The tube is 9.2 across at the root, so against either of those the rails at the
arm's flanks never enter the pole's cylinder at all, and the 10-across boot cannot hide behind a
pole narrower than itself. The first report of this (#197) was a curve floating beside a
pedestal pole with its open end showing.

A real arm on a slim pole is not welded on either. It is bolted to a **bracket**, and that is what
the root cell draws when the pole behind it is narrow:

* the boot-free tube, **cut flat** where it enters a plate — the very cut listed as wrong above,
  which was wrong *against a bare round pole* because nothing covered the flanks. Behind a flat
  plate wider than the tube it is the only cut that fits;
* a **plate** standing `PLATE_GAP` off the pole's front skin, sized per preset off the tube's own
  cut ring plus `PLATE_MARGIN` all round. It is measured rather than guessed because a steeper
  preset's oblique cut is a taller ellipse, and it also sits *lower*: the parabola keeps dropping
  behind the pole face, so the 6x2 plate's bottom edge reaches about a unit into the block below;
* a **saddle block** behind the plate whose back is a concave arc just inside the pole's skin, so
  it hugs the pole all the way across instead of touching it along one line;
* two **band straps** round the pole, top and bottom of the plate.

All of that is drawn by the root cell and sits in the pole's block. An OBJ may leave its block;
the root is right behind it, so this is never the only thing keeping the bracket on screen.

**The arm adapts to the pole, not the other way round.** `BlockTrafficPoleMastArmCurve`'s root
asks `CsmPoleFit.behind()` (Core) what stands behind it, which reads
`AbstractBlockTrafficPole.getPoleRadius()` and picks `LARGE` (saddle boot), `THIN` or
`PEDESTAL` (bracket) by the midpoints between the radii the joints were generated for. Anything
that is not a pole gets the large fit, whose saddle cut simply disappears inside a full block
(a luminaire arm draws a back plate there instead; see "Luminaire arms").
The pole draws nothing at the joint either way: curves are `ICsmTrafficPoleIgnored`, as before.
The root packs the fit into its `shape` slot rather than carrying `CsmPoleFit.PROPERTY` the way
the light mounts do (see "Pole fit" in `BLOCK_AND_ITEM_BASE_CLASSES.md`), because its model
already depends on the cell and the mount mask and one property is all a blockstate can key a
model off.

The root's mount stubs are shared with the large root wherever the meshes agree, which is
everywhere except a stub that anchors inside the boot (the `down` stub on every preset, `east`
and `west` on 6x2). Those few get their own files; the generator compares the meshes and writes a
separate stub only when it has to, and searches the *large* root's parameter span so the
comparison is not defeated by a shifted sample grid.

## Luminaire arms

The same machinery carries street lights (GitHub #99): `gen_luminaire_arms.py` writes the truss
arms (Hapco's RTA bracket; 8, 10, 12 and 15 ft) and the Caltrans arms (6, 8, 10, 12 and 15 ft),
each single or double, each with a curved or a straight upsweep, in the pole family's six colours
(galvanized, silver, black, white, tan, concrete): 216 blocks, `luminairearm<size><finish>`, a
straight one `luminairearm<size>straight...`. They are `BlockTrafficPoleMastArmCurve`s built from a
`LuminaireArmProfile` rather than a `MastArmCurveProfile`; the block works through
`ICurvedArmProfile`, which both enums satisfy (the mast arm one through a small adapter, so its
generator and output are untouched). Placement, all-or-nothing, demolition and the measured
hitboxes are the curves' own.

**Scale and shape.** The street lights are drawn about 1.2-1.4 times true size, so the arms are
too, at 1.4: a 6 ft arm runs 2 blocks from the pole's face, a 15 ft arm 6. The tip ends at
`y 1.375` on the last cell's far face, the centre of `ARM_TIP` in `gen_streetlight_fixtures.py`:
place any street light against the tip and its neck takes the arm. A truss arm has an upper member
(3'3" rise, 3.6 across at the root and 2.8 at the tip, a 5.4 boot), a straight lower member leaving
the pole 2'0" lower and meeting the upper two thirds out, and one vertical strut a third out; the
lower root sits in the block under the arm's root, beside the pole. **A Caltrans arm is the truss
arm of its length without the lower member and the strut**, at the same rise (the requester's
review, 2026-11; they were Caltrans' ES-6A davits, lower and fatter, before). The 6 ft one, which
no truss matches, keeps Caltrans' own 1'6" rise and tube. Arms placed before that change keep their
old cell indices and have to be broken and placed again.

**Curved or straight (`upsweep`).** Curved is the curves' parabola, level at the tip. Straight
climbs at one slope to an elbow 0.7 of a block short of the tip and runs level from there, the
corner eased over a 0.7 block parabolic bend so the tube turns without a crease. Either way the
tip arrives level, which is what a fixture's neck needs.

**Los Angeles and Anaheim arms.** `laupsweep8ft/10ft/12ft` are the 1950s-60s Los Angeles upsweep
davits (the black museum pole in BSL frame 02): the Caltrans tube with a steeper rise (4'6", 5'0",
5'6" at 1.4), and a thin straight tie rod leaving the pole 14 px under the root and meeting the arm
45% of the way out; galvanized, silver and black. `anaheim8ft` is City of Anaheim Special Design
#749's arm: an 8 ft run whose tip stands 3'3" over the pole top (26'4" against the 23'1" pole), a
slimmer tube, and the cast scroll work under it drawn as a brace from lower on the pole rising
smoothly into the arm, with a curl hung in the angle; it comes in Anaheim green only
(`FINISHES_FOR`), and sits on `decopoleanaheim` with a GE cobra head at its tip, as the drawing
specifies. The brace and the tie rod are pole members, so they get saddle cuts per fit like the
truss's lower member.

**The Van Nuys Special.** `vannuystriple` is Los Angeles' three-headed light (BSL CD-955, Van
Nuys Boulevard, early 1970s): a pitchfork laid flat over the road. The pole parts at its top, at
one point, into three slim tubes, each one smooth arc from straight up to level; the middle one
reaches straight out, the outer two splay to either side, and all three end at the same height
and reach. It was first built as three arms nested in one vertical plane, which is what the
Bureau's well-known photo, taken along the street, looks like; a view from across the street
shows the level row, and the requester corrected it. So it stands **on** the pole: the block is
placed on the pole's top face and is the fork (a short flared socket, no pole joint, so no fit
variants), and it reaches the way the placer faces. The tips are two blocks apart at the far face
of the fourth block out, two rows up, so three street lights fit side by side. It is the one arm
that leaves its plane: `Member.side` gives a centreline a sideways offset (here `sin^2` of the
arc's angle, so the tube leans neither where it leaves the fork nor where it meets the fixture),
cells are `{along, up, side}`, and the profile's offsets have three elements, which the block
already understood for the diagonal truss arms.

**Double arms.** The second arm is the first turned half round about the pole, so its cells are at
negative `alongArm` (two blocks behind the root and on), each cell's model the first arm's turned
about its own block centre.

**The pole joint.** A luminaire arm is narrower than every CSM pole, so each member that starts at
the pole is saddle-cut against the pole's own cylinder for all three `CsmPoleFit` widths: no
bracket. The generator compares each cell's mesh across the fits and only the cells that differ
(the roots: one per member at the pole, per arm) get fit variants. `ICurvedArmProfile.poleSide`
names those cells and which side their pole is on (`1` behind, `-1` ahead for a double arm's
second root), and the block reads `CsmPoleFit.behind` that way. There is no mount hardware on a
luminaire arm, so a `shape` value is a slot alone: the cell index, or a slot past the last cell
for a pole-joint cell on a narrower pole.

**On a wooden pole or a wall: the back plate** (GitHub #349). Against a full block that is not a
CSM pole there is no cylinder to cut against, and the large fit's tube just ran into the block:
an arm with nothing holding it. A pole-joint cell there draws a fourth joint, `wall`: every
member that starts at the pole is cut flat at a plate standing 0.7 off the block's face, one
plate tall enough to span all of them (on a truss arm, from under the lower member to over the
upper one, as the truss brackets lagged to wooden utility poles in New England are built), with
four bolt heads. It is not a `CsmPoleFit`, which other blocks' blockstates enumerate; the block
passes it separately (`ICurvedArmProfile.shapeIndex(cell, mask, fit, againstFullBlock)`), and a
joint cell takes three slots past the cells' own instead of two. "A full block" is any log
(`BlockLog`, so other mods' wood too) or any opaque cube. The plate is cut at a block boundary
only between two cells that each hold a member's joint: handed to whichever cell it lay in, a
plate's margin made a new joint cell with its own block to test, and the plate lost its top to
the air above a pole.

**Not done:** mount stubs along a luminaire arm; the pole colours for the Los Angeles arms and
the Van Nuys Special (galvanized and silver, black too on the LA arms; green on the Anaheim arm).

## Truss signal mast arms

The two-chord signal arms of Massachusetts, New Hampshire and New Jersey (GitHub #99), where a
monotube arm would be used elsewhere: `gen_truss_signal_arms.py`, 24 blocks,
`trusssignalarm<id><finish>` in galvanized, silver and black. One block places the whole arm,
pole to tip; there is no upsweep handing off to `trafficpolehorizontal`.

| Id | Shape | Cells |
|---|---|---|
| `level6`, `level8`, `level10`, `level12` | top chord straight and level, bottom chord climbing from 20 px lower on the pole to meet it at the tip (Boston, MassDOT) | 10, 13, 16, 19 |
| `sloped8`, `sloped12` | both chords climbing 1 and 2 blocks over the run and converging at the tip (New Jersey) | 14, 21 |
| `diagonal5`, `diagonal8` | a level-top arm at 45 degrees in plan, 5 and 8 diagonal steps (7.1 and 11.3 blocks) | 8, 13 |

They are `BlockTrafficPoleMastArmCurve`s built from the generated `TrussSignalArmProfile`.

**Every member is a straight pipe**, so a member is cut only where it crosses a cell boundary: one
band per member per cell. A 12 block arm is about 800 triangles in all. The top chord is 5.2
across, the bottom 4.2, the struts 2.5; a level top chord is centred in its row exactly as
`trafficpolehorizontal` is, so a signal head against it lines up as on a monotube arm.

**The pole joint** is the luminaire arms': each chord saddle-cut against the pole's cylinder per
`CsmPoleFit`, plus a clamp collar round the pole. The two cells holding a chord's pole end are the
only ones with fit variants.

**A diagonal arm moves itself on placement.** Its first cell is diagonal to the pole, where there
is no face to click. So it is placed against a pole's face like every other arm, and
`onBlockPlacedBy` then removes the placed block and lays the arm from one step to its right:
placed on the north face it reaches north-east, on the east face south-east, and so on round. The
profile expresses that as a non-zero offset for cell 0 (`getCellOffset` may return a third,
sideways value) and a `getPoleOffset` of one back and one left. Its cells sit on the lattice the
angled thin traffic pole uses (`trafficpolehorizontalangle*`), one per diagonal step; consecutive
cells touch only at an edge, which is that family's rule and why the generator does not assert
face adjacency for it.

**Mount hardware is per cell, and so is the packing.** `ICurvedArmProfile.getMountDirections(cell)`
names the sides a cell can grow a stub on, out of six (down, up, east, west, ahead, back); the
block tests only those. A side that is another cell of the same arm never can, a cell holding only
the bottom chord hangs things below it, and only a diagonal arm uses ahead and back. A `shape`
value is `base[cell] + fit * 2^n + mask`, the mask holding that cell's own `n` sides, so a level
12 arm is 170 shape values where a uniform `cell * 16 + mask` would be over 300. A stub clamps to
whichever chord is nearest the face it reaches (a sign under the arm hangs from the bottom chord)
and identical stub meshes are written once (`trusssignalarm_stub_<n>.obj`) and shared across
cells and arms.

**A head hung from the tip.** Put a wire mount (`tlitevertwiremount` / `tlitehorzwiremount`)
under a cell and a signal head under the mount, and the cell grows its down hardware to the
mount's bracket: the New Jersey arrangement, a head swinging under the end of the arm. Poles
ignore the whole accessory family the wire mounts belong to, so `isMountableAdjacent` says no;
`BlockTrafficPoleMastArmCurve.isHangingWireMount` is the one exception, for the down side only,
and only while the mount is not linked into a span (a linked mount hides its bracket and is
carried by the span's own hardware, which this must not touch). It applies to the mast arm curves
too. A head placed directly under a cell, with no mount between, stands half a block into the
cell and through the pipe: the mount is what gives it room.

**Each cell says where its pipes are.** `ICurvedArmProfile.getCellRails(cell)` returns the
centreline segments passing through a cell (`{x0, y0, z0, x1, y1, z1, radius}`, cell frame), and
`BlockTrafficPoleMastArmCurve.getWorldRails` turns them to the arm's facing. The truss profile
carries them generated; a mast arm curve's are two chords of its parabola a block, computed in
the block from the run and rise (the generator's `centre` and `radius`, restated there: change
one, change the other). Luminaire arms return none. The one user is the dynamic street name
sign, whose hangers stop at the pipe over them: DYNAMIC_STREET_SIGN_SYSTEM.md, "Hangers".

**Not done:** the curved-top truss (Boston City Hall; New Hampshire's signal arms); a mirrored
diagonal (the arm always turns to the right of the face it was placed on, so the other diagonal is
reached from the next face round).

### The New York City arm

The guyed arm of every signalized corner in New York City, from the same generator as a second
family (`FAMILIES`): 15 blocks, `nycsignalarm<id><finish>` in brown, galvanized and black, regular
4/6/8 blocks and diagonal 4/6 steps, enum `NycSignalArmProfile`. One tapered pipe (2.8 px at the
pole, 1.9 at the tip) leaves a clamp collar low on the pole at three times the slope it settles
to, and two half-pixel guy rods run from the ends of a crossbar higher on the pole (11 px either
side of its axis; the crossbar is a block and a half long, as the city's are) in to the tip fitting.

It is a level truss arm with other members. The rods are where the top chord is, so the block is
placed at the rods' height (which is the height the head hangs from) and the pole has to reach one
block lower for the 4, two for the others, where the pipe's collar lands (`GUYED_FOOT`). The pipe
is where the bottom chord is. What it added to the generator:

- **A bend.** The pipe's first 36 px are four straight members; where two meet they share one
  ring on the bisector of their axes (`Member.ring_a` / `ring_b`) and neither is capped. The
  stations (`GUYED_STATIONS`) are kept clear of every cell boundary of both the regular and the
  diagonal arm, so a boundary ring never lands on a mitre.
- **Taper.** `Member.r_b`; everything that asked a member its radius now asks `radius(u)`.
- **Members beside the diagonal.** A rod on a diagonal arm runs a pixel or two off the diagonal,
  so cutting it at the world's x and z planes would hand slivers to cells that are not the arm's.
  For `guyeddiagonal` a member is cut where it passes from one diagonal step to the next
  (`diagonal_q`), and `cell_of` assigns by step.
- **Two members, one collar.** The crossbar is two pole members, one out of each side of the
  pole (saddle-cut per `CsmPoleFit`, which makes cell 0 a joint cell); the first carries the
  band, the second has `collar_r=False`. The crossbar is the same length on every pole, so the
  rods themselves do not depend on the fit and only cell 0 does. It overhangs the blocks either
  side of the arm; `cell_of` keeps a regular arm's geometry in the arm's own column (`side = 0`)
  and its members are not cut at x planes, so no cell appears beside the arm for it.

Only the pipe is a chord: it takes hardware below and beside it (never above, where the rods are)
and is the only rail a street name sign's hangers find. A cell holding nothing but rods grows
nothing. The tip stops 3.5 px past the middle of the last cell, not at its far face, so the down
stub of that cell, and a wire mount hung there, is at the very end of the arm.

The brown finish is `metal_brown`, which the generator tints from `metal_silver` (`BROWN_RGB`);
`--check` compares its pixels, not the encoder's bytes.

**Not done:** the newer straight arm with no guy rods; the M-2 pole itself.

## Geometry details worth not rediscovering

**Boundary crossings get one sample, not a straddling pair.** The sweep injects a sample wherever
the centerline crosses a cell boundary, so no band spans two cells. Inserting a *pair* at
`t ± 1e-6` looks safer and is not: the band between them is 2e-6 long, its two rings coincide, and
every triangle in it is a zero-area sliver. One sample exactly on the crossing achieves the goal,
because the bands then abut there. The generator asserts on any band shorter than 1e-3.

**Diagonal steps are repaired.** When the centerline crosses a row boundary and a column boundary
at the same `t` — which for a parabola is not exotic; `6x2` does it exactly at `t = 3` — the two
occupied cells touch only along an edge. That leaves a hole a player can walk through and, worse,
breaks the block adjacency the auto-connect work will need. The generator inserts the cell that
advances along the arm first and hands it the destination's first band. The tube is thick enough
that its surface genuinely passes through that cell, so the fix is geometric, not cosmetic. The
generator asserts that no cell ends up owning zero geometry.

**UVs never leave the sprite.** Block textures live in an atlas, so a UV outside 0..1 samples a
*neighbouring* sprite instead of tiling. A ping-pong (mirrored) wrap into the sprite's middle half
keeps texel density roughly constant along a tube of any length and never touches the border,
where `CUTOUT_MIPPED` mip levels would bleed. The metal swatches are near-flat (std ≤ 8/255), so
the mirror seam is invisible.

## Verifying a change

```bash
python dev-env-utils/scripts/gen_mast_arm_curves.py
python dev-env-utils/scripts/audit_obj_models.py <the emitted .obj files>
```

The audit must report no FAIL, no coplanar overlap and no faces on a block boundary. `winding` and
`see-through` warnings need reading rather than obeying: each cell is an open-ended slice of a
tube, so it has 16 boundary edges per open end by construction, and rays entering those openings
legitimately hit back faces first.

## Not done yet

**Auto-connect along the curve.** The blocks are there and are adjacency-visible, which was the
whole point of the multi-block layout, but nothing yet renders a mount stub on a sloped tube.
Doing it properly means stub geometry that meets the tube at the local tangent angle, which
varies per cell — so the stubs would be generated per cell alongside the tube, and the block
would move from `AbstractBlockRotatableNSEW` to the `AbstractBlockTrafficPole` family to pick up
the `MOUNT_*` properties. See `UTILITIES_SYSTEM.md` and `AbstractBlockTrafficPole` for how the
existing mount properties work.

**Free-form sizing.** The presets are fixed blocks. A single block whose run/rise are chosen from
a GUI is possible on this foundation — the cell layout is already data — but every combination
would need its geometry pre-baked, since the models are static OBJ.
